## 2. 세부 성능 변천사 (기존 테스트 이력)

```
[ 초기 상태 (4채널 profile2) ]
  • 4개 채널 모두 2592x1520 초고해상도로 수신
  • 채널당 ~14.5ms 소요되어 4채널 동시 처리 시 CPU 점유율 급증 및 프레임 지연 발생
                                    │
                                    ▼ (1단계: 저해상도 서브스트림 도입)
[ Phase 1: 4분할 profile10 적용 ]
  • 640x480 서브스트림으로 대역폭 및 CPU 지연을 1.98ms로 대폭 단축 성공
  • 한계: 카메라 설정상 15fps로 제한되고, 4:3 해상도로 인해 16:9 모니터에서 비율 왜곡 발생
                                    │
                                    ▼ (2단계: 와이드 서브스트림 & 초저지연 옵션)
[ Phase 2: 4분할 profile4 + 1채널 확대 profile2 동적 전환 ⭐ (최종) ]
  • 4분할 모드: profile4 (800x448 @ 35.6fps) 적용 ──▶ 총 처리 지연 `0.88 ms` 달성!
  • 1채널 확대 모드: profile2 (2592x1520 @ 35.6fps) 적용 ──▶ 400만 화소 초고화질 선명도 제공 (`6.86 ms`)
```

## 3. Latency를 어떻게 줄였는가? (핵심 최적화 기법 5가지)

### ① 동적 프로파일 분기 (Dynamic RTSP Profile Switching)
- **문제점**: 4개 타일을 모두 2592x1520 원본으로 디코딩하면 화면에는 작게(960x562) 축소되어 표시되는데도 연산량은 4배로 낭비됨.
- **해결**:
  - 평상시 4분할 화면: 가벼운 **`profile4` (800x448 서브스트림)**으로 수신하여 프레임당 처리 시간을 **0.88ms**로 단축.
  - 1채널 확대(솔로 모드) 클릭 시: 사용자가 보고 있는 채널만 **`profile2` (2592x1520 메인스트림)**로 동적 전환하여 리소스 낭비 원천 차단.

### ② FFmpeg 초저지연 프로빙 및 제로 버퍼링 (`nobuffer` & `low_delay`)
- **문제점**: FFmpeg 기본 설정(`avformat_open_input`)은 네트워크 지터를 방지하기 위해 5MB 이상의 패킷을 수집하고 수 초간 스트림을 분석(Probing)하여 초기 지연 및 내부 버퍼 딜레이 발생.
- **해결**:
  - `AVDictionary` 옵션 최적화:
    ```cpp
    av_dict_set(&opts, "fflags", "nobuffer", 0);        // 내부 수신 큐 버퍼링 제거 (즉시 전달)
    av_dict_set(&opts, "flags", "low_delay", 0);         // 저지연 플래그 활성화
    av_dict_set(&opts, "probesize", "65536", 0);         // 스트림 분석 크기를 64KB로 최소화
    av_dict_set(&opts, "analyzeduration", "100000", 0);   // 분석 시간을 100ms로 단축
    av_dict_set(&opts, "max_delay", "100000", 0);        // 최대 지연 허용 100ms
    m_fmt->flags |= AVFMT_FLAG_NOBUFFER | AVFMT_FLAG_FAST_SEEK;
    ```
  - 네트워크 패킷이 도착하자마자 버퍼링 없이 즉시 디코더로 주입되어 실시간 지연 시간(Glass-to-Glass) 극소화.

### ③ H.264 디코더 코덱 플래그 최적화
- **해결**:
  ```cpp
  m_codec->flags |= AV_CODEC_FLAG_LOW_DELAY;   // 프레임 재정렬(B-Frame 지연) 대기 비활성화
  m_codec->flags2 |= AV_CODEC_FLAG2_FAST;      // 고속 H.264 루프 필터 및 가속 모드 활성화
  ```
- 비디오 프레임이 수신되는 즉시 0.72ms 만에 CPU 디코딩 완료.

### ④ 마지막 프레임 유지 (Seamless Freeze Transition)
- **문제점**: 프로파일 전환 시 이전 스트림이 끊기면서 0.5~1초 동안 검은 화면/플레이스홀더가 깜빡여 사용자가 지연을 크게 체감함.
- **해결**:
  - 스트림 재접속 중에도 이전 화면의 마지막 프레임을 화면에 그대로 Freeze 상태로 유지.
  - 새 스트림의 첫 I-Frame이 디코딩되는 순간 즉시 교체되어 **체감 끊김/블랙아웃 0초 달성**.

### ⑤ 동적 SWS 스케일러 컨텍스트 캐싱 및 버퍼 재사용
- **해결**:
  - 해상도나 포맷이 변경되지 않는 한 `sws_getContext` 및 RGB 메모리 버퍼를 매 프레임 할당/해제하지 않고 영구 캐싱하여 메모리 할당(`malloc`/`free`) 오버헤드 완전 제거 (스케일링 0.16ms).

## 4. 향후 GPU 하드웨어 가속 도입 시 비교 로드맵

추후 GPU 디코더(D3D11VA / DXVA2 / NVDEC) 도입 시 예상되는 성능 비교 지표입니다:

| 비교 항목 | 현재 (CPU 디코더) | 향후 (GPU 하드웨어 가속) 예상 | 개선 효과 |
| :--- | :---: | :---: | :--- |
| **2592x1520 H.264 디코딩** | `4.91 ms` | **`0.8 ~ 1.2 ms`** | GPU 전용 비디오 ASIC 디코더 엔진 활용 |
| **YUV $\rightarrow$ RGB 컬러 변환** | `1.95 ms` | **`0.05 ~ 0.1 ms`** | GPU Direct 텍스처 바인딩 (Zero-Copy) |
| **호스트 CPU 점유율** | 약 5 ~ 15% | **`0 ~ 1%` 수준** | CPU를 AI 객체 인식 및 라이다 PCD 처리에 전량 집중 가능 |
